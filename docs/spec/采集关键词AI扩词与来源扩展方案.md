# 采集关键词 AI 扩词与来源扩展方案（规格）

> 状态：阶段一（AI 扩词）已实现，2026-10-29 合入 main；阶段二（来源扩展）尚未实施。实现计划见 `docs/plan/采集扩词与来源扩展-实现计划.md`。

## 1. 背景与问题

1. **关键词靠手填**：每个分类的「GitHub 主题（≤8）」「GitHub 关键词（≤4）」「HF Spaces 搜索词（≤6）」「给模型的分类说明（≤500 字）」都要管理员自己写。不熟悉生态时不知道该填什么、填的词是否真有结果、会不会和别的分类撞车。
2. **来源太窄**：现有 5 个来源里，MCP Registry 和 awesome 清单只覆盖 MCP，HF 只看 Spaces，Product Hunt 需要 Token；实际上大部分候选来自 GitHub 搜索。「AI 编程」「AI 模型/API」「AI 创作」「Agent Skills」等分类缺少对口来源，而且非开源产品（只有官网、没有仓库）几乎采不到。

## 2. 目标

- **A. AI 扩词**：每个关键词字段旁加「魔法棒」按钮，按分类语境生成候选词；鼠标悬浮可看每个词的语义、推荐理由和真实命中数；点选加入输入框，保存前不落库。
- **B. 扩词规则**：后台统一的规则约束 AI 输出（格式、数量、去重、跨分类不重叠、过泛/无结果过滤），规则由代码执行，不只靠提示词。
- **C. 来源扩展**：新增若干免费、公开 API 的来源，让每个分类都至少有一个非 GitHub 的对口来源；awesome 清单从「写死一个」改为「每个分类可配多个（白名单格式校验）」。

## 3. 不做

- 不让 AI 直接改配置并保存；一律人工点选 + 保存。
- 不抓取需要登录或明确禁止爬取的站点（Reddit API 需 OAuth、各类 AI 导航站的条款限制），不绕过反爬。
- 不做关键词效果的长期统计报表（二期可基于 `CollectRun.notes` 做「哪个词带来了被采纳的候选」）。

## 4. A：AI 扩词

### 4.1 交互

- 适用字段：GitHub 主题、GitHub 关键词、HF 搜索词（以及新来源各自的搜索词字段），外加「给模型的分类说明」（魔法棒生成一版草稿，替换前二次确认）。
- 点击字段标签旁的 ✨ 魔法棒 → 弹层显示 6–12 个候选词「词签」，状态分三种：
  - **推荐**：格式合法、有命中、不重叠；可点。
  - **过泛**：命中数超过上限（如 GitHub 主题 > 20,000 个仓库），可点但标黄。
  - **不可用**：无结果 / 与其他分类重复 / 已在输入框；置灰不可点，悬浮说明原因。
- **悬浮提示**（tooltip）：
  - 语义：这个词在该生态里指什么（≤40 字）
  - 推荐理由：为什么适合本分类、和相近分类怎么区分
  - 命中：「GitHub 约 1,240 个仓库（star ≥ 100）」/「HF 约 85 个 Space」
- 点词签 → 追加到输入框（受字段上限约束，满了提示「已达上限，先删一个」）；「全部加入推荐」一键追加到上限。
- 输入框仍可手改；最终以「保存」按钮为准。
- 生成中按钮转圈；失败给出原因（未配置模型 / 超时），不影响表单。

### 4.2 AI 输入（分类语境）

- 分类名称与 slug、当前「分类说明」。
- 本分类已上架资源样例：最多 15 条的名称 + 标签 + 一句话简介。
- 当前字段已有的词；本分类其他字段已有的词。
- **其他分类**已配置的同类词（用于避免重叠）及其分类名。
- 字段规则摘要（格式、上限、语言），见 4.3。

模型输出 JSON：`[{ term, meaning, reason }]`，要求 8–15 个，按推荐程度排序。

### 4.3 扩词规则（代码执行）

| 规则 | GitHub 主题 | GitHub 关键词 | HF 搜索词 |
|---|---|---|---|
| 格式 | 复用现有 zod：小写字母数字连字符 ≤50 | 2–40 字符，文字数字空格 . + # - | 2–40 位 `A-Za-z0-9._-` |
| 语言 | 英文（GitHub topic 惯例） | 英文短语为主 | 英文 |
| 上限 | 字段剩余名额 × 2 个候选 | 同左 | 同左 |
| 去重 | 大小写/连字符/空格归一后与已有词比较 | 同左 | 同左 |
| 跨分类 | 与其他分类同字段词归一后相同 → 不可用 | 同左 | 同左 |
| 泛词黑名单 | `ai` `llm` `tool` `tools` `app` `awesome` `python` `javascript` 等单独出现 → 不可用 | 同左 | 同左 |
| 命中校验 | GitHub 搜索 `topic:x stars:>=新秀门槛` 取 total_count；0 → 不可用，>20,000 → 过泛 | `"x" in:name,description,topics stars:>=门槛`；阈值同左 | `/api/spaces?search=x` 取前 100 的条数；0 → 不可用 |

- 规则集中在 `lib/agent/term-rules.ts`，纯函数、可测；阈值常量可调。
- 命中校验有速率成本：无 GitHub Token 时搜索接口 10 次/分钟，所以最多校验前 8 个候选，其余标「未校验」；有 Token 时全部校验。结果按「分类 + 字段 + 词」缓存 24 小时。
- 规则版本号写进提示词与结果，方便日后调整后识别旧建议。

### 4.4 成本与安全

- 每次点击 1 次模型调用（≈ 2–3k token），沿用现有模型配置；同一分类同一字段 10 分钟内重复点击走缓存。
- 仅管理员可用（Server Action + `requireAdmin`）；模型输出只当数据，经规则过滤后返回，绝不直接写库。

## 5. C：来源扩展

### 5.1 新增来源（一期）

均为公开、免费、无需登录的接口；实施前逐个核实接口与条款，结论回写本节。

| 来源 | 接口（待核实） | 适合分类 | 每分类配置 |
|---|---|---|---|
| Hacker News「Show HN」 | `hn.algolia.com/api/v1/search?tags=show_hn` | AI 编程、AI 创作、模型/API（含非开源产品） | 搜索词，最低分数，时间窗 |
| Hugging Face 模型 | `huggingface.co/api/models` | AI 模型/API | 搜索词 / pipeline 标签，按趋势或点赞 |
| OpenRouter 模型列表 | `openrouter.ai/api/v1/models` | AI 模型/API | 仅开关（只取新上架模型） |
| awesome 清单（可配） | GitHub raw README | 所有分类 | 每分类最多 3 个仓库，格式 `owner/repo`，只读 raw.githubusercontent.com |

- awesome 清单：从写死的 `punkpeye/awesome-mcp-servers` 改为分类级配置，仍限制只能是 GitHub 仓库（不接受任意 URL，沿用 SSRF 防护）；解析器从「MCP 章节关键词」改为通用列表项解析。MCP 分类的配置迁移时默认填入原清单。
- 魔法棒同样适用于新来源的搜索词字段，并可「推荐 awesome 清单」（AI 给出候选仓库，经 GitHub API 校验仓库存在、star 与最近更新后展示）。

### 5.2 来源框架统一

- 每个来源实现同一接口：`fetch(config, ctx) → RawCandidate[]`，声明自己的配置 schema、默认值、适合的分类提示、是否需要 Token。
- 全局开关（采集 Agent 设置）+ 分类级开关与参数（分类采集配置），与现有方式一致。
- 运行详情里按来源显示「拉到 N 条 / 错误」，已有。
- 二期候选：Smithery / Glama 等 MCP 目录（需确认 API 与授权）、GitHub Trending（无官方 API，暂不做）、Reddit（需 OAuth，暂不做）。

## 6. 验收标准

1. 任一分类点 GitHub 主题旁的魔法棒，10 秒内出现 ≥6 个候选，悬浮可见语义、理由、命中数。
2. 与其他分类重复、已存在、无结果、泛词的候选置灰并说明原因；点选只改输入框，刷新页面不丢已保存配置。
3. 字段满额时不能再加入，提示清楚。
4. 未配置模型时按钮给出「请先配置模型」，不报错。
5. 新增 4 个来源 + 可配 awesome 清单均可在分类上开启，运行详情显示各来源条数；任一来源失败不影响其他来源。
6. 「AI 编程」「AI 模型/API」「AI 创作」「Agent Skills」各自至少有一个非 GitHub 来源能产出候选。
7. 现有分类配置迁移后行为不变（MCP 分类仍读原 awesome 清单）。
8. 规则与来源解析均有单元测试（fixture），现有测试全部通过。

## 不采用的来源（2026-10-26 决定）

- npm：包数量大但噪音多（热门结果混入通用小工具、适配器），且多数与 GitHub 仓库重复，增量有限。
- 通用搜索引擎（Yandex、Google、Bing 等）：官方搜索 API 收费或已停止对新用户开放，直接抓取结果页违反条款；返回的是网页而非结构化资源，难以去重与判定分类。
