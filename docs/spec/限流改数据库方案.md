# 限流改数据库方案

> 状态：已实现（2026-10-29，分支 db-rate-limit），待预览验收后合 main。
> 背景：前台推荐 Agent 的前提之一（《Agent 方案》§二、MVP §2.4、架构 §5）。

## 1. 现状与问题

- `lib/auth/rate-limit.ts`：内存 `Map` 固定窗口，10 分钟 5 次，只在登录 `authorize` 里用。
- **多实例无效**：Vercel 每个函数实例各有一份 `Map`，冷启动即清零，攻击者换实例就能绕过，实际几乎拦不住。
- **只按邮箱计数**：
  - 任何人拿管理员邮箱连续输错 5 次，就能把真管理员锁 10 分钟（低成本拒绝服务）。
  - 换邮箱撞库不受限（不存在的邮箱也照样查库 + bcrypt）。
- 前台推荐 Agent 每次请求都花模型费用，必须有跨实例可靠的按 IP 限流。

## 2. 目标与不做

目标：
- 跨实例、跨冷启动可靠的通用限流，登录先用上，前台推荐 Agent 直接复用。
- 不引入新的外部服务（以后自托管时 compose 里只有 PostgreSQL，Upstash 会多一个依赖）。
- 不存原始 IP。

不做：
- 滑动窗口、令牌桶等更精细算法（固定窗口够用）。
- 每日花费上限（另写方案，和推荐 Agent 一起做；本方案只提供可复用的计数能力）。
- 验证码、二次验证。

## 3. 方案：Postgres 固定窗口计数

### 3.1 数据表

```prisma
/// 通用限流计数（固定窗口）。key = 桶名 + ":" + 主体哈希，不存原始 IP / 邮箱。
model RateLimit {
  key       String   @id
  count     Int
  expiresAt DateTime

  @@index([expiresAt])
}
```

迁移：`2026xxxx_rate_limit`，只新增表，不动现有数据。

### 3.2 原子计数（一条 SQL）

用数据库时间，避免各实例时钟不一致；一条 `INSERT … ON CONFLICT` 完成「窗口过期则重置，否则 +1」，并发安全：

```sql
INSERT INTO "RateLimit" (key, count, "expiresAt")
VALUES ($1, 1, now() + make_interval(secs => $2))
ON CONFLICT (key) DO UPDATE SET
  count       = CASE WHEN "RateLimit"."expiresAt" <= now() THEN 1 ELSE "RateLimit".count + 1 END,
  "expiresAt" = CASE WHEN "RateLimit"."expiresAt" <= now() THEN now() + make_interval(secs => $2) ELSE "RateLimit"."expiresAt" END
RETURNING count, "expiresAt";
```

用 `prisma.$queryRaw` 执行；每次判断只多一次往返（Neon 同区约几毫秒）。

### 3.3 模块接口（`lib/security/rate-limit.ts`，替换 `lib/auth/rate-limit.ts`）

```ts
type Bucket = { name: string; limit: number; windowSec: number };

/** 计一次；超过 limit 返回 ok=false 与需要等待的秒数 */
hit(bucket: Bucket, subject: string): Promise<{ ok: boolean; remaining: number; retryAfterSec: number }>;
/** 同时检查多个桶，任何一个超限即拒绝（都会计数） */
hitAll(checks: [Bucket, string][]): Promise<{ ok: boolean; retryAfterSec: number }>;
/** 成功后清零（如登录成功清掉「邮箱+IP」桶） */
reset(bucket: Bucket, subject: string): Promise<void>;
```

- **主体哈希**：`subject` 先做 `HMAC-SHA256(AUTH_SECRET, subject)` 取前 32 位十六进制再拼进 key，库里看不到 IP 和邮箱原文（与站内统计的隐私做法一致）。
- **取 IP**：复用 `lib/analytics/visitor.ts` 的 `clientIp(headers)`（取 `x-forwarded-for` 第一个，其次 `x-real-ip`）；取不到时用 `"unknown"`，这类请求共用一个桶，宁可误伤也不放行。
- **桶配置集中**放在同一文件的常量里，方便审阅和测试；判断逻辑（窗口是否过期、retryAfter 计算）抽成纯函数写单元测试。
- **数据库出错**：抛出，由调用方决定。登录本来就依赖数据库，出错即登录失败（拒绝）；推荐 Agent 同样拒绝（不能在限流失效时放开花钱）。

### 3.4 过期清理

- 每次 `hit` 以 1% 概率顺带执行 `DELETE FROM "RateLimit" WHERE "expiresAt" < now() - interval '1 hour'`（不等待结果）。
- 每日定时采集接口开头也清一次。
- 行数上限可控：登录桶按 IP / 邮箱+IP，数量极小；推荐 Agent 上线后按 IP，日活规模也就几百到几千行。

## 4. 登录限流新规则

在 `authorize` 里（直接 POST `/api/auth/callback/credentials` 也会经过这里，不能只在 server action 里拦）：

| 桶 | 主体 | 上限 | 作用 |
| --- | --- | --- | --- |
| `login:ip` | IP | 20 次 / 5 分钟 | 拦住单 IP 撞库 / 换邮箱试 |
| `login:email-ip` | 邮箱 + IP | 5 次 / 5 分钟 | 单账号试密码；成功登录后清零 |
| `login:email` | 邮箱 | 30 次 / 1 小时 | 分布式慢速爆破兜底；阈值放宽，避免一个人就能锁住管理员 |

- 先限流再查库和 bcrypt，超限直接拒绝，省掉 bcrypt 的 CPU。
- 超限时抛自定义 `CredentialsSignin`（`code = "rate_limited"`），登录页提示「尝试过于频繁，请 N 分钟后再试」；密码错误仍是原提示，不暴露邮箱是否存在。
- IP 从 `authorize` 的 `request.headers` 取。已核实（next-auth 5.0.0-beta.32 / @auth/core 0.41.3）：server action 的 `signIn` 先用 `next/headers` 复制真实请求头再构造 Request，`authorize` 收到的 request 带原始 `x-forwarded-for`，无需改用 `headers()`。

## 5. 前台推荐 Agent 预留（不在本次实施）

推荐 Agent 上线时直接加桶，例如：`recommend:ip` 每分钟 5 次、每天 50 次；全站每日调用次数 / 花费上限另行设计。

## 6. 自托管时的注意

- 方案只依赖 PostgreSQL，迁移到自托管不用改代码。
- 反向代理（Caddy / Nginx）必须**覆盖**而不是追加 `X-Forwarded-For`（或只信任最后一跳），否则客户端可以伪造 IP 绕过按 IP 限流。写进自托管部署文档。

## 7. 验收

1. 单元测试：窗口判断、retryAfter 计算、多桶任一超限即拒绝、主体哈希不含原文。
2. 本地 Postgres 集成验证：并发 20 次 `hit` 计数准确（无丢失更新）。
3. 预览环境：同一邮箱连续输错第 6 次提示「过于频繁」；换浏览器 / 等函数冷启动后仍被拦；另一个 IP 用该邮箱仍可登录（不被锁死）；正确密码登录后「邮箱+IP」计数清零。
4. `RateLimit` 表中看不到 IP / 邮箱原文；过期行能被清理。
5. 架构 §5、Agent 方案「前提」更新为已完成。
