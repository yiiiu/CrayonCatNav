# 自托管部署与定时调度方案（规格）

> 状态：规格草案（2026-10-26），尚未实施。实现计划见 `docs/plan/自托管部署-实现计划.md`。

## 1. 背景

目前生产部署在 Vercel + Neon，定时采集靠 `vercel.json` 的 Vercel Cron 每天 UTC 01:00 调 `/api/cron/collect`。后续不再使用 Vercel，改为**自己的 Ubuntu / Linux 服务器 + Docker** 部署，数据库用 **compose 内自带的 PostgreSQL**。

Vercel Cron 离开 Vercel 就不存在了；而 Serverless 下跑不起来的进程内调度器，在常驻的 Node 进程里可以正常使用。借这次迁移把定时能力改成与平台无关，并让运行时间可以在后台修改。

## 2. 目标

1. 一条命令（`docker compose up -d`）在一台 Linux 服务器上跑起完整站点：应用 + PostgreSQL + 自动迁移。
2. 定时采集由应用自己调度，**时间和开关都在后台可改，保存后立即生效**，无需重新部署。
3. 不能重复运行：同一时刻只有一个采集在跑（多容器或手动 + 定时同时触发也不行）。
4. 代码中不再依赖任何 Vercel 专有能力；保留在 Vercel 上运行的可能，但不再作为目标。
5. 有基本的运维保障：健康检查、日志、数据库备份、从 Neon 迁移数据的步骤。

## 3. 不做

- 多实例横向扩容（cacheComponents 的内存缓存与 `updateTag` 只在单实例下一致；多实例需要共享 cache handler，另议）。
- K8s、CI/CD 自动发布（先手动 `git pull && docker compose up -d --build`，后续可加 GitHub Actions）。
- 消息队列 / 分布式任务框架（BullMQ、pg-boss 等）；任务量只有每天几次，杀鸡不用牛刀。
- 前端监控、APM。

## 4. 部署形态

```
┌──────────── Linux 服务器（Docker） ────────────┐
│  反向代理（Caddy / Nginx，宿主机或容器，负责 HTTPS） │
│        │ :3000                                    │
│  app     Next.js standalone（node server.js）      │
│          └─ 进程内调度器（croner）                  │
│  migrate 一次性容器：prisma migrate deploy + seed   │
│  db      postgres:17，数据卷持久化                  │
└───────────────────────────────────────────────┘
```

- **app**：`output: "standalone"` 构建的最小镜像，非 root 运行，监听 3000，`restart: unless-stopped`。
- **migrate**：用构建阶段镜像（含 prisma CLI、tsx）执行 `prisma migrate deploy && prisma db seed`，成功后退出；app 通过 `depends_on: condition: service_completed_successfully` 等它完成。迁移与运行分离，运行镜像不带 CLI。
- **db**：官方 `postgres:17-alpine`，命名卷持久化，只在内部网络暴露，不映射公网端口；带 `pg_isready` 健康检查。
- **反向代理**：推荐 Caddy（自动 HTTPS）。方案里给出 Caddyfile 示例，是否容器化由部署时决定。

## 5. 定时调度

### 5.1 机制

- 用 **croner**（零依赖、支持时区与标准 cron 表达式、可暂停/重建）在应用启动时注册任务。
- 入口：Next.js `instrumentation.ts` 的 `register()`，仅在 `NEXT_RUNTIME === "nodejs"` 且 `SCHEDULER_ENABLED=true` 时启动调度器。
- 任务到点直接调用领域层 `runCollection("cron")`，不再绕 HTTP。
- `/api/cron/collect` **保留**，作为外部触发的备用入口（宿主机 crontab、监控平台等），仍用 `CRON_SECRET` 鉴权。

### 5.2 配置（存库，后台可改）

`AgentSetting` 新增：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `cronEnabled` | Boolean | true | 已有 |
| `cronExpr` | String | `0 9 * * *` | 5 段 cron 表达式 |
| `cronTimezone` | String | `Asia/Shanghai` | IANA 时区 |

后台「定时采集」区：开关 + 时间设置。默认提供常用选项（每天 HH:MM、每 N 小时、每周几），高级模式可直接填 cron 表达式；保存前校验表达式合法、最小间隔不少于 1 小时，并预览「接下来 3 次运行时间」。

### 5.3 生效方式

- 启动时读库建任务。
- 后台保存设置后，在同一进程内调用 `scheduler.reload()` 立刻重建任务（单实例部署，Server Action 与调度器同进程）。
- 兜底：调度器每 10 分钟比对一次库里的配置版本（`updatedAt`），变化则重建，防止以后出现多进程时漏刷新。

### 5.4 防重复与容错

- 继续用现有 `AgentSetting.lockedUntil` 运行锁：拿不到锁就跳过并记日志，手动采集与定时采集互斥。
- 只在一个容器上设 `SCHEDULER_ENABLED=true`；即便误开多个，运行锁也保证不会并发。
- 进程重启错过的时间点**不补跑**（采集不是强时效任务），后台显示「上次定时运行」便于发现漏跑。
- 单次运行不再受 Vercel 300 秒限制，但保留超时（默认 10 分钟）以防卡死，超时会释放锁并记失败。

### 5.5 后台展示

- 开关、运行时间说明（北京时间）、接下来 3 次运行时间。
- 调度器状态：运行中 / 未启用（`SCHEDULER_ENABLED` 未开）/ 配置无效。
- 上次定时运行时间与结果（取自 `CollectRun` 中 `trigger = cron` 的最近一条）。

## 6. 去 Vercel 化清单

| 位置 | 现状 | 处理 |
|---|---|---|
| `vercel.json` crons | Vercel Cron | 删除，改进程内调度 |
| `package.json` `vercel-build` | 构建时迁移 + seed | 删除，迁移交给 migrate 容器 |
| `lib/site.ts` | 回退读 `VERCEL_URL` 等 | 只认 `NEXT_PUBLIC_SITE_URL`；缺失时开发环境回退 localhost |
| `NEXT_PUBLIC_SITE_URL` | 构建时内联 | 作为 Docker 构建参数传入，文档说明改域名需重建镜像 |
| `export const maxDuration` | Vercel 函数时长 | 自托管下无作用，可保留不删；AI 批量补全等上限可视情况放宽 |
| Auth.js | Vercel 上自动信任 Host | 设 `AUTH_TRUST_HOST=true`，反代需传 `X-Forwarded-Proto/Host` |
| `prisma.config.ts` | `DATABASE_URL_UNPOOLED`（Neon） | 自带 PG 无连接池，直接用 `DATABASE_URL` |
| 预览部署 | Vercel 分支预览 | 改为本地 `docker compose` 验收，或服务器上另起 staging compose 项目 |

## 7. 环境变量

`.env.production`（不入 git）：`DATABASE_URL`、`POSTGRES_PASSWORD`、`AUTH_SECRET`、`AUTH_TRUST_HOST=true`、`AGENT_ENCRYPTION_KEY`、`CRON_SECRET`、`NEXT_PUBLIC_SITE_URL`、`SCHEDULER_ENABLED=true`、`SEED_ADMIN_EMAIL/PASSWORD`（首次部署后删除）、可选 `GSC_SITE_URL`、`BING_*`、`GOOGLE_SITE_VERIFICATION`。

注意：`AGENT_ENCRYPTION_KEY` 必须与 Vercel 上的一致，否则从 Neon 迁过来的已保存 API Key 无法解密，需要在后台重新填写。

## 8. 运维

- **健康检查**：新增 `/api/health`（查一次数据库），compose `healthcheck` 与反代都用它。
- **日志**：stdout，`docker compose logs`；compose 配置日志轮转（json-file `max-size`）。
- **备份**：宿主机 crontab 每天 `pg_dump` 到本地目录并保留 14 天，脚本放 `deploy/backup.sh`。
- **数据迁移**：Neon → 自建 PG：`pg_dump --no-owner --no-acl` 导出、`pg_restore` 导入，导入后 `migrate deploy` 应为无待执行迁移。
- **升级**：`git pull && docker compose up -d --build`；迁移容器自动先跑。

## 9. 验收标准

1. 全新 Ubuntu 机器装好 Docker 后，按文档 `cp .env.example .env.production` 填值、`docker compose up -d`，站点可访问，后台可登录。
2. 后台把定时改为「几分钟后」，到点自动产生一条 `trigger = cron` 的运行记录；关掉开关后不再产生。
3. 改时间保存后无需重启，「接下来 3 次运行」与实际触发一致。
4. 定时运行期间点「开始采集」提示已有采集在运行。
5. 重启 app 容器后调度自动恢复；数据库数据不丢。
6. `docker compose down && up` 后迁移容器显示无待执行迁移。
7. 代码中不再出现 `VERCEL_` 环境变量与 `vercel.json`。
8. 现有测试全部通过，新增调度、表达式校验、配置重建的单元测试。

## 10. 风险

| 风险 | 应对 |
|---|---|
| `instrumentation.ts` 在 dev 热更新时重复注册 | 调度器做成全局单例（`globalThis`），注册前先停旧任务 |
| 单机故障即全站不可用 | 接受（MVP 规模）；有每日备份，恢复流程写进文档 |
| 内存缓存随容器重启丢失 | 只是冷启动慢一点，数据在库里，不影响正确性 |
| 构建期需要数据库（cacheComponents 预渲染读库） | 构建阶段在 compose 内可连 db，或让读库页面在请求时渲染；计划中先验证 |
