# 自托管部署 + 进程内定时调度：实现计划

> 规格：`docs/spec/自托管部署与定时调度方案.md`。状态：计划（2026-10-26），未开始实施。
> 分支：从 main 新开分支开发，本地 `docker compose` 验收后再合 `main`。

## 0. 已定决策

| 决策 | 结论 | 原因 |
|---|---|---|
| 部署目标 | 自有 Ubuntu/Linux + Docker Compose | 用户确定不再用 Vercel |
| 数据库 | compose 内 `postgres:17-alpine` | 用户确定 |
| 调度器 | croner + `instrumentation.ts` | 常驻进程可用；零依赖、支持时区 |
| 迁移 | 独立 migrate 一次性容器 | 运行镜像不带 prisma CLI / tsx |
| 实例数 | 单实例 | cacheComponents 内存缓存一致性 |
| 错过的时间点 | 不补跑 | 采集非强时效 |
| 外部触发入口 | 保留 `/api/cron/collect` | 备用；成本为零 |

## 1. 待验证（实施第一步，结论回写本节）

1. **构建期是否需要数据库**：当前 `pnpm build` 需连库（cacheComponents 预渲染读库）。方案 A：先 `docker compose up -d db`，`build.network` 指向 compose 网络、构建参数传 `DATABASE_URL`；方案 B：把读库页面全部改为请求时渲染，构建不连库。优先 A，B 改动面大。
2. `instrumentation.ts` 在 standalone `server.js` 下 `register()` 只调用一次（Next 16 文档：`node_modules/next/dist/docs/` 中 instrumentation 一节）。
3. `next/image` 在 standalone 下是否需显式装 `sharp`。
4. Prisma 7 adapter-pg 在 alpine 下无需额外引擎（adapter 模式不依赖原生引擎，确认即可）。

## 2. 任务拆分

### T1 数据库字段与校验（约 0.5 天）
- `prisma/schema.prisma`：`AgentSetting` 加 `cronExpr String @default("0 9 * * *")`、`cronTimezone String @default("Asia/Shanghai")`、`lastCronAt DateTime?`。
- 迁移 `prisma/migrations/2026xxxx_agent_cron_schedule/migration.sql`（`migrate diff` 生成后手改）。
- `lib/validation/agent.ts`：`cronExpr` 用 croner 解析校验；最小间隔 ≥ 1 小时（取接下来 2 次运行时间差）；`cronTimezone` 用 `Intl.supportedValuesOf("timeZone")` 校验。
- 测试：合法/非法表达式、间隔过短、非法时区。

### T2 调度器（约 1 天）
- 新增依赖 `croner`。
- `lib/scheduler/collect-scheduler.ts`（server-only）：
  - `globalThis` 单例；`start()`、`reload()`、`stop()`、`status()`。
  - `reload()` 读 `AgentSetting`：关闭或表达式无效则停任务；否则 `new Cron(expr, { timezone, protect: true }, run)`。
  - `run()`：调 `runCollection("cron")`，捕获 `DomainError`（含拿不到锁）记日志；成功或失败都写 `lastCronAt`。
  - 每 10 分钟比对 `updatedAt`，变化则 `reload()`（兜底）。
- `lib/scheduler/schedule.ts`（纯函数）：`nextRuns(expr, tz, n)`、`describeSchedule(expr, tz)`（「每天 09:00（北京时间）」等），替代现有 `lib/agent/cron-schedule.ts`。
- `instrumentation.ts`（web 根）：`register()` 中 `NEXT_RUNTIME === "nodejs" && SCHEDULER_ENABLED === "true"` 时动态 import 并 `start()`。
- `lib/domain/collector.service.ts`：运行超时（默认 10 分钟）后释放锁并记失败。
- 测试：`nextRuns` / `describeSchedule`；`reload` 在开关、表达式变化时的行为（mock repo 与 Cron）。

### T3 后台界面（约 1 天）
- `components/admin/AgentSettingsForm.tsx`「定时采集」区：
  - 开关；频率选择（每天 HH:MM / 每 N 小时 / 每周几 HH:MM / 自定义 cron），用现有 `components/ui/Select`；时区默认北京时间。
  - 「接下来 3 次运行」预览（客户端按表单值实时计算，调用纯函数）。
  - 调度器状态：运行中 / 未启用（`SCHEDULER_ENABLED` 未开）/ 配置无效；上次定时运行时间与结果。
- `lib/domain/agent-settings.service.ts`：view 增加上述字段；`saveSettings` 成功后调用 `scheduler.reload()`。
- 去掉「运行时间由 vercel.json 固定」提示。

### T4 去 Vercel 化（约 0.5 天）
- 删除 `vercel.json`、`package.json` 的 `vercel-build`；`lib/agent/cron-schedule.ts` 及其测试由 T2 取代。
- `lib/site.ts`：只认 `NEXT_PUBLIC_SITE_URL`，开发环境回退 `http://localhost:3000`。
- `prisma.config.ts`：保留 `DATABASE_URL_UNPOOLED ?? DATABASE_URL`（兼容），文档说明自建 PG 只需 `DATABASE_URL`。
- Auth.js 配置确认 `trustHost`（或环境变量 `AUTH_TRUST_HOST=true`）。
- `.env.example` 更新：去掉 Neon/Vercel 说明，加 `POSTGRES_PASSWORD`、`AUTH_TRUST_HOST`、`SCHEDULER_ENABLED`。

### T5 Docker 化（约 1 天）
- `next.config.ts`：`output: "standalone"`。
- `web/Dockerfile` 多阶段：
  - `deps`：`node:22-alpine` + corepack pnpm，`pnpm install --frozen-lockfile`。
  - `builder`：复制源码，`prisma generate`，`pnpm build`（`NEXT_PUBLIC_SITE_URL`、构建期 `DATABASE_URL` 作为 build-arg，见 §1-1）。
  - `migrator`：基于 builder，`CMD prisma migrate deploy && prisma db seed`。
  - `runner`：`node:22-alpine`，复制 `.next/standalone`、`.next/static`、`public`，非 root 用户，`EXPOSE 3000`，`HEALTHCHECK` 访问 `/api/health`，`CMD node server.js`。
- `web/.dockerignore`：`node_modules`、`.next`、`generated`、`.env*`、测试产物。
- 根目录 `docker-compose.yml`：`db`（卷 `pgdata`、`pg_isready` 健康检查、不映射公网端口）、`migrate`（target migrator，`depends_on: db healthy`）、`app`（target runner，`depends_on: migrate completed_successfully`，`env_file: .env.production`，`ports: 127.0.0.1:3000:3000`，日志轮转）。
- `app/api/health/route.ts`：`SELECT 1`，返回 `{ ok: true }`；失败 503。

### T6 运维脚本与文档（约 0.5 天）
- `deploy/Caddyfile.example`（域名 → `127.0.0.1:3000`）。
- `deploy/backup.sh`：`docker compose exec -T db pg_dump` 压缩到 `/var/backups/crayon`，保留 14 天；附 crontab 示例。
- `deploy/migrate-from-neon.md`：`pg_dump --no-owner --no-acl` → `pg_restore`；导入后 `migrate deploy` 应无待执行迁移；`AGENT_ENCRYPTION_KEY` 必须沿用。
- `docs/部署.md`：从零部署、升级、回滚（上一个镜像 tag）、备份恢复、常见问题。
- `README.md`、`docs/蜡笔猫导航-v1-架构.md` §9 更新部署与调度说明；项目简报更新。

## 4. 实施顺序

T1 → T2 → T3（功能闭环，可在现有环境跑测试）→ T4 → T5 → T6。T1–T3 一个提交，T4–T6 一个提交，便于回滚。

## 5. 验收

按规格 §9 逐条执行，另加：
- 沙箱无 Docker 守护进程时，至少完成：`pnpm test / typecheck / lint` 通过、`docker compose config` 校验通过；真实 `docker compose up` 由用户在服务器或本机执行，验收清单写进 `docs/部署.md`。
- 镜像体积目标 < 300 MB。

## 6. 风险与回退

- 构建期连库方案不通 → 改走 §1-1 方案 B，单独评估工作量后再继续。
- 迁移到新服务器期间：Vercel 生产保持运行，自建环境验收通过、数据迁移完成后再切 DNS；切换前关闭 Vercel 上的 Cron（或删 `CRON_SECRET`），避免两边同时采集。
- 回退：DNS 切回 Vercel；Neon 数据在切换后不再更新，回退需反向导数据。

约 4.5 人天（不含服务器准备与 DNS）。
